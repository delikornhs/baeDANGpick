### 성장 원인과 속도
- 매일 `--prices-only` 실행이 915개 파일 전부를 다시 쓰고(끝에 하루치 append), 이게 데일리 커밋에 포함됨.
- 다만 파일 끝에 붙이는 형태라 git delta 압축이 잘 먹어, **실제 이력 증가는 하루 수백 KB 수준**으로 추정 (29MB가 매일 쌓이는 게 아님). 연 환산 대략 수십~100MB대.
- **결론: 급하지 않음. 1~3년 내 관리 이슈.** GitHub 권장 저장소 크기 <1GB(소프트), 문제 발생 ~5GB.

### 방식 선택을 좌우하는 핵심 제약 2가지
1. 파일이 **웹에서 fetch 가능**해야 함 (현재는 Vercel이 git째로 배포해서 같은 출처로 서빙).
2. 종가 차트에 **"전체" 옵션**(상장이후 전 구간)이 있어 → 파일을 최근 N년으로 잘라내는 방식은 이 기능을 깨뜨림.

## 분리/완화 옵션

### ① 오브젝트 스토리지로 이전 (근본 해결) — Cloudflare R2 권장
git에서 완전히 빼고, 데일리 job이 R2/Vercel Blob에 업로드 → 사이트는 그 URL에서 fetch.
- **장점**: git 비대화 문제 완전 해결, 무한 확장.
- **단점**: 외부 서비스 + GitHub Action에 인증 secret 추가 / fetch URL이 외부 호스트로 바뀌어 **CORS 설정 필요** / R2는 egress 무료라 적합하나 계정·설정 관리 부담 / fetch 실패 모드가 외부 호스트에 의존.
- **적기**: 이력 증가가 실제 문제(예: `.git` 500MB~1GB 근접)가 됐을 때의 정공법.

### ② 별도 데이터 저장소/브랜치로 분리
price_history만 별도 repo(예: `baedangpick-data`)나 orphan 브랜치로 옮겨 별도 배포.
- **장점**: 코드 repo는 깔끔해짐. 데이터 repo는 코드 이력과 무관하게 주기적으로 통째 리셋 가능.
- **단점**: 교차 출처 fetch → CORS / 배포 파이프라인 2개 / 데이터 repo 자체는 여전히 커짐(위치만 옮긴 것).
- **성격**: "코드 이력 보호 + 데이터는 언제든 날려도 됨"이 목적일 때만 의미. 실익 애매.

### ③ 주기적 이력 정리 (현 구조 유지, 가장 저비용)
구조·코드 그대로 두고, 1년에 한 번 정도 `git filter-repo`나 orphan 브랜치 리셋으로 price_history 과거 blob을 날림. (이 파일들의 날짜별 git 이력은 아무도 안 보므로 버려도 무방)
- **장점**: 아키텍처·사이트 코드 변경 없음, 같은 출처 유지, 외부 서비스 불필요.
- **단점**: 이력 재작성 = force-push라 데일리 자동화와 타이밍 조율 필요, 수동 정기 작업.
- **성격**: 상시 전략이라기보다 "비대화 임계 도달 시 눌러주는 밸브".

### ④ 증가 속도 완화 (분리는 아니고 보조책)
- **④-a 롤링 윈도우**: 각 파일을 최근 N년만 저장 → 큰 파일들이 확 줄어듦.
  - ⚠️ **단, 차트 "전체" 옵션과 충돌** → 이 기능을 포기하거나 "전체 = 최근 N년"으로 재정의해야 함.
- **④-b JSONL 포맷**: 배열 대신 한 줄 = 하루로 바꿔 순수 append만 발생 → git delta 최적화로 증가율 최소화.
  - "전체" 유지 가능. 클라이언트(etf.html·compare.html) 파싱 소폭 수정 필요.

## 추천 (단계별)

1. **지금**: 구조 변경 없이 유지. 가끔 `.git` 크기만 체크(`du -sh .git`). 하루 수백 KB 수준이라 당장 문제 아님.
2. **증가가 눈에 띌 때 (저비용 1순위)**: **④-b(JSONL 전환)** — "전체" 기능 유지하면서 증가율을 크게 낮춤. 클라이언트 수정도 작음.
3. **실제 문제화되면 (정공법)**: **① Cloudflare R2** 이전으로 git에서 영구 분리.

- ②는 "위치만 옮김 + CORS·배포 이중화"라 실익이 애매.
- ③은 상시 전략보다 임계 도달 시 1회성 정리용으로만 권함.

### 이번에 확인한 사실 두 가지

**1. 과거 종가는 재조회해도 절대 바뀌지 않는다.**
7/22 커밋본과 7/24 커밋본에서 겹치는 날짜 **14,859일을 비교한 결과 값이 달라진 날 0개**.
→ 이 파일들의 **git 과거 버전은 보관 가치가 전혀 없다**. 현재 버전이 과거 버전을 완전히 포함하고(검증: `oldset ⊆ newset` True), 네이버에서 언제든 재조회도 가능하다.

**2. 매일 전체를 재조회하는 현재 방식에는 숨은 장점이 있다.**
`fetch_daily_price_history()`가 매일 상장일~오늘 전체를 새로 받아 덮어쓰므로, **파일이 손상돼도 다음 날 자동 복구**된다. 증분(하루치만 append) 방식으로 바꾸면 이 자가복구가 사라지고 파일이 유일한 사본이 된다.

### 자주 하는 오해 (실제로 헷갈렸던 지점)

| 오해 | 사실 |
|---|---|
| "증분 조회로 바꾸면 용량이 준다" | **아니다.** 줄어드는 건 네트워크 요청량·소요 시간(15분→2~3분)이고, 파일은 여전히 전체 이력을 담아야 하므로(차트가 전 구간을 그림) git 저장 용량은 동일하다. |
| "git 과거 버전을 지우면 차트의 과거 구간이 사라진다" | **아니다.** 매일 저장되는 파일은 '그날까지의 전체 이력'이라 최신 파일 하나에 전부 들어 있다. 과거 버전은 중복 사본일 뿐이다. |
| "연 1회 정리는 매일 정리보다 안전하다" | **아니다.** 작업(이력 재작성) 자체의 위험도는 같다. 다를 뿐인 건 빈도이고, 자동화 대신 사람이 지켜보며 할 수 있다는 점이다. |
| "필요 없는 파일이니 지우는 건 간단하다" | 파일 삭제는 간단하지만, **git에서 과거 버전만 골라 지우는 건 불가능**하다. `git filter-repo`로 전체 커밋(현재 409개)을 다시 쓰고 force-push해야 하며, 모든 클론이 재동기화해야 하고, GitHub이 공간을 즉시 회수하지도 않는다. |
